# النشر

[English](deployment.md)

البناء والفحص باستخدام Go **1.27.3** وNode **22.23.4** وnpm **10.9.2** وDocker
Engine وCompose v2 على Linux. تخدم عملية Go واحدة API وملفات Webpack؛ لا يوجد Node
أو Redis أو خادم قاعدة مستقل بالإنتاج. تحتاج SQLite والملفات قرصاً محلياً دائماً
خارج مجلد الإصدار، وليس NFS. لا تشغّل مثيلين؛ يمنع قفل التشغيل خادماً ثانياً على
جذر البيانات نفسه.

انسخ `.env.example` إلى ملف خاص خارج Git واستبدل كل القيم المؤقتة. يقرأ Go البيئة
ولا يقرأ dotenv تلقائياً. للأوامر الأصلية حمّل ملف shell موثوقاً عبر
`set -a; . /private/blog.env; set +a`. استخدم نطاق HTTPS ومعرّف RP فعليين ومتطابقين؛
تغيير النطاق يحتاج إعادة تسجيل مفاتيح المرور ولا ينقل اعتماد المزود تلقائياً.
تُرفض نطاقات `.invalid` بالإنتاج. جهز مجلدات البيانات والنسخ ومفتاحاً ثنائياً
منفصلاً بطول 32 بايت، بصلاحيات خاصة للمشغل وUID/GID 65532:

```sh
sudo install -d -m 700 -o 65532 -g 65532 /srv/personal-blog/data /srv/personal-blog/backups /srv/personal-blog/secrets
sudo sh -c 'umask 077; test ! -e /srv/personal-blog/secrets/auth-key && openssl rand 32 > /srv/personal-blog/secrets/auth-key'
sudo chown 65532:65532 /srv/personal-blog/secrets/auth-key
# من جذر المستودع وبملف البيئة الخاص الفعلي.
docker compose --env-file /private/blog.env -f deploy/compose.yml build
# احتفظ بتصريح المالك سرياً؛ لا يُزرع مالك أو محتوى.
docker compose --env-file /private/blog.env -f deploy/compose.yml run --rm blog bootstrap
docker compose --env-file /private/blog.env -f deploy/compose.yml up -d
docker compose --env-file /private/blog.env -f deploy/compose.yml exec -T blog /app/blog ready
```

اضبط Caddy على المضيف بالملف المرفق و`BLOG_HOSTNAME` وDNS والمنفذين 80/443. يكشف
Compose المنفذ 8080 للحلقة المحلية فقط. اضبط CIDRs للوكيل الفعلي فقط ولا تثق
بترويسات تمرير عشوائية. يحذر بدء الإنتاج عند غياب الوكلاء الموثوقين؛ خلف Docker
ثق فقط بعنوان الوكيل المرصود (وقد يكون بوابة الجسر)، وليس بكل العملاء.
لا تسجل الاستعلامات أو ملفات الارتباط أو الاعتمادات أو
الأجسام. أكمل الإعداد عبر `/ar/login` واختبر عاملاً احتياطياً مستقلاً ورموز استرداد
غير متصلة. اضبط الاسم والهوية والملف والترجمات من اللوحة دون تعديل المصدر أو
محتوى مزروع. راجع [أمان المالك](owner-security.ar.md).

قبل الترقية تحقق من نسخة مشفرة حديثة خارج الخادم ونسخة المفتاح المنفصلة وفحوص
المرشح، وأوقف الخادم القديم وانسخ بالصورة **القديمة قبل أن يفتح أي أمر من الإصدار
المرشح القاعدة**. قد يرحّل أي أمر أصلي أو Compose run القاعدة عند البدء. مثال
مع الخدمة القديمة قيد التشغيل:
`docker compose --env-file /private/blog.env -f deploy/compose.yml exec -T blog /app/blog backup --file /backups/pre-upgrade.zip`.
شفّر وانقل النسخة ثم أوقف الخدمة واختر الصورة المختبرة وشغّل `up -d` وافحص
الجاهزية والدخول والمراجعات والوسائط. افصل البيانات عن الإصدارات. لا تشغّل كوداً
قديماً غير متوافق على مخطط مرحّل. فضّل الإصلاح الأمامي؛ الرجوع يتطلب الصورة
القديمة ونسختها السابقة للترقية في مجلد جديد وفق دليل الاستعادة. يبطل الاسترجاع
الاعتمادات وتقدم القراء. احتفظ بالبيانات الفاشلة للتشخيص.

يشمل [دليل الاستعادة](operations/recovery.md) إعادة التسجيل وهدف 24 ساعة
وسبع نسخ يومية وأربع أسبوعية. نجاح الصحة مع جاهزية 503 بعد الاستعادة مقصود حتى
اختبار العامل الجديد و`blog resume`. عند فشل البدء افحص السجلات المنقحة والملكية
والنطاق/RP وطول المفتاح وبيان البناء والمخطط؛ لا تحذف SQLite أو تتجاوز التحقق.
راجع [التغطية الفعلية](release-readiness.ar.md)؛ بناء الصورة لا يثبت
نشر الإنتاج.
