# دليل النشر والتشغيل (Deployment)

[English](deployment.md)

تعتمد عمليات البناء والاختبار على Go **1.27.3** وNode **22.23.4** وnpm **10.9.2** ومحرك Docker مع Compose v2 على أنظمة Linux. تتولى عملية تشغيلية واحدة بلغة Go خدمة واجهة البرمجة (API) وأصول Webpack المترجمة؛ ولا تتطلب بيئة الإنتاج وجود بيئة Node.js أو خادم Redis أو خادم قاعدة بيانات منفصل. تتطلب قاعدة بيانات SQLite وملفات المراجعات والوسائط وحدة تخزين محلية دائمة خارج مجلد حزم الإصدار، ولا تدعم العمل على أنظمة الملفات الشبكية مثل NFS. احذر تماماً من تشغيل مثيلين من التطبيق؛ حيث يمنع عقد الإيجار التشغيلي (runtime lease) إقلاع أي خادم ثانٍ على جذر البيانات نفسه.

انسخ الملف `.env.example` إلى ملف خاص خارج شجرة مستودع Git، واستبدل كافة القيم المؤقتة بالقيم الحقيقية الخاصة بك. يقرأ الملف التنفيذي لـ Go متغيرات البيئة من النظام مباشرة ولا يقرأ ملفات `.env` تلقائياً. ولتشغيل الأوامر الأصلية المباشرة، حمّل ملف متغيرات بيئة موثوقاً في الطرفية عبر: `set -a; . /private/blog.env; set +a`. استخدم اسم نطاق HTTPS حقيقياً ومطابقاً بدقة لمعرف الطرف المعتمد (RP ID)؛ فتغيير النطاق لاحقاً يفرض إعادة تسجيل كافة مفاتيح المرور (passkeys) ولا ينقل بيانات اعتماد المزود السحابي تلقائياً. تُرفض نطاقات النماذج الافتراضية مثل `.invalid` في بيئة الإنتاج. جهز مجلدات خاصة للبيانات والنسخ الاحتياطية، وأنشئ مفتاح تشفير ثنائياً منفصلاً بطول 32 بايت، مع قصر صلاحيات الوصول على المشغل والمستخدم ذي المعرف UID/GID 65532 فقط:

```sh
sudo install -d -m 700 -o 65532 -g 65532 /srv/modawana/data /srv/modawana/backups /srv/modawana/secrets
sudo sh -c 'umask 077; test ! -e /srv/modawana/secrets/auth-key && openssl rand 32 > /srv/modawana/secrets/auth-key'
sudo chown 65532:65532 /srv/modawana/secrets/auth-key
# نفّذ الأوامر من المجلد الجذري للمستودع مع تمرير ملف البيئة الخاص من /private/blog.env
docker compose --env-file /private/blog.env -f deploy/compose.yml build
# احتفظ بتصريح المالك الأولي في مكان سري؛ لا يتضمن النظام أي مالك أو محتوى تجريبي مُعد مسبقاً
docker compose --env-file /private/blog.env -f deploy/compose.yml run --rm blog bootstrap
docker compose --env-file /private/blog.env -f deploy/compose.yml up -d
docker compose --env-file /private/blog.env -f deploy/compose.yml exec -T blog /app/blog ready
```

اضبط خادم Caddy على الجهاز المضيف باستخدام ملف Caddyfile المرفق، مع تعيين اسم النطاق الفعلي `BLOG_HOSTNAME`، وضبط سجلات DNS، وفتح المنفذين 80 و443. يقتصر Compose على كشف المنفذ 8080 على واجهة الاسترجاع المحلية (loopback) فقط. حدد نطاقات عناوين IP للوكلاء الموثوقين (CIDRs) لتطابق عناوين الوكلاء الفعلية المرصودة فقط؛ ولا تثق أبداً بترويسات التمرير القادمة من أطراف مجهولة. يُظهر التطبيق تحذيراً عند بدء التشغيل في الإنتاج في حال عدم ضبط وكيل موثوق؛ وخلف شبكة Docker، احرص على حصر الثقة في عنوان نظير الوكيل المرصود فقط (والذي قد يكون عنوان بوابة الجسر الافتراضية bridge gateway)، وليس كافة العملاء. احرص على خلو ملفات السجلات من سلاسل الاستعلامات، وملفات تعريف الارتباط، وبيانات الاعتماد، ومتون الطلبات. أكمل إعداد حساب المالك عبر الرابط `/ar/login`، وسجّل عاملاً احتياطياً مستقلاً واختبره، واحتفظ برموز استرداد غير متصلة بالإنترنت. خصص اسم الموقع، وهويته البصرية، وملفك الشخصي، وترجمات النصوص من لوحة التحكم دون الحاجة لتعديل الكود المصدري أو زرع محتوى مسبق. راجع وثيقة [أمان المالك](owner-security.ar.md).

قبل إجراء أي ترقية مستقبلية: تأكد من وجود نسخة احتياطية مشفرة وحديثة خارج الخادم ونسخة منفصلة لمفتاح التشفير، وتحقق من اجتياز اختبارات التكامل المستمر وصور الحاويات المرشحة، ثم أوقف الخادم القديم، وخُذ نسخة احتياطية باستخدام **صورة الحاوية السابقة قبل أن يفتح أي أمر من الإصدار المرشح الجديد قاعدة البيانات**. حيث قد يؤدي أي أمر تنفيذي أصلي أو تشغيل عبر Compose إلى تطبيق الترحيلات على قاعدة البيانات فور الإقلاع. مثال لأخذ النسخة الاحتياطية أثناء تشغيل الخدمة القديمة:
`docker compose --env-file /private/blog.env -f deploy/compose.yml exec -T blog /app/blog backup --file /backups/pre-upgrade.zip`.
قم بتشفير هذه النسخة ونقلها خارج الخادم، ثم أوقف الخدمة، واختر صورة الحاوية الجديدة التي تم اختبارها، وشغّل الأمر `up -d`، وتحقق من مؤشرات الجاهزية، وتسجيل الدخول، ومراجعات المحتوى، وخدمة الوسائط المرفوعة. احرص دائماً على الفصل التام بين ملفات الإصدارات وصورها وبين مجلد البيانات الدائم. لا تُشغّل أبداً ملفاً تنفيذياً قديماً غير متوافق على قاعدة بيانات تم ترقية مخططها. ويُفضل دائماً حل المشكلات للأمام (forward fix)؛ بينما تتطلب العودة للإصدار السابق (rollback) استخدام صورة الحاوية القديمة المطابقة واستعادة نسختها الاحتياطية السابقة للترقية في مجلد جديد وفق دليل الاستعادة. يؤدي إجراء الاستعادة عمداً إلى إبطال بيانات الاعتماد وتصفير تقدم القراء. واحتفظ بالبيانات المتعثرة لتشخيص أسباب المشكلة.

يوضح [دليل الاستعادة والاحتفاظ بالبيانات](operations/recovery.md) خطوات الاستعادة دون اتصال، وإعادة تسجيل المفاتيح، وهدف نقطة التعافي (RPO) البالغ 24 ساعة، والاحتفاظ بسبع نسخ يومية وأربع نسخ أسبوعية. إن إرجاع فحص الصحة لرمز النجاح 200 مع بقاء فحص الجاهزية على رمز الخطأ 503 بعد الاستعادة هو سلوك مقصود لحماية النظام حتى يتم اختبار تسجيل العامل الجديد وتشغيل الأمر `blog resume`. وعند فشل بدء التشغيل، راجع السجلات المنقحة، وصلاحيات ملكية الملفات، وتطابق النطاق ومعرف RP ID، وطول المفتاح السري، وبيان الأصول، وتوافقية مخطط قاعدة البيانات؛ ولا تحذف أبداً ملف SQLite أو تتجاوز التحقق من الترحيلات. راجع دليل [جاهزية الإصدار](release-readiness.ar.md) للتحقق من التغطية الفعلية في البيئة المستهدفة؛ فمجرد نجاح بناء صورة الحاوية لا يعني اكتمال النشر والقبول في الإنتاج.
